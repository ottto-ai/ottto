# Private validated upload receipt evidence

Normal local Codex and Claude snapshot uploads can retain bounded diagnostic evidence in the existing owner-only upload receipt ring. The destination-scoped sync client supplies its existing one-way namespace; the transport hashes its effective API base separately. Existing public v1 receipt DTOs and diagnostics expose the same redacted projection. Older disk rows have no annotation and remain readable.

Capture requires the explicit entity ACK contract and successful existing request-specific identity, occurrence, body-witness and effective head-CAS validation. Disabled and legacy count-only responses never produce proof. The hook runs before later stricter sync reconciliation and checkpoint settlement: a valid request ACK is not proof of a completed source cycle, a new accepted occurrence, or SESSION execution. Accepted, unchanged, conflict and rejected remain distinct; repeated requests retain their multiplicity. Conflict challenges never become accepted heads.

Private annotations retain full valid hex semantic fingerprints and request body digests, separate request envelope and acknowledged witness versions, domain-separated session hashes, hashed accepted heads or challenges, producer version, attempt identity, server request correlation, and destination hashes. They contain no raw session IDs, head tokens, URLs, prompts, or rejection details. Unknown ACK witnesses and heads remain null. Capture uses the effective request passed to transport and does not change delivery, CAS, ACK validation, progress, acquisition, or retry behavior.

The annotation also records actual uploaded cache-patch presence and the request's `request_count` and `output_tokens` values. These content-free scalars support later changed-field correlation; they do not supply backend sequence numbers, receive timestamps or prior values. Accepted head tokens remain hashed here. An owner can compare that hash with the token already retained by the existing authoritative progress ledger; no additional raw-token retention is needed.

Each annotation retains at most 50 outcome references, exact request multiplicity and validated outcome occurrences for each retained reference, total distinct request entities, total requested occurrences and per-outcome occurrence counts. Coverage explicitly says complete or truncated. Full request validation precedes truncation. The existing ring retains at most 500 receipts under a shared 4 MiB file cap; oldest receipts are evicted under byte pressure so new bounded records remain recordable. Atomic owner-only persistence, corrupt-state quarantine and clear semantics remain shared. Receipt I/O errors leave the original upload result unchanged.

Focused tests exercise invalid and foreign ACKs, missing or wrong witnesses/heads, short fingerprints, duplicate and incomplete occurrence partitions, legacy/disabled responses, mixed outcome multiplicity, public redaction, old disk rows, truncation, byte-pressure eviction, restart reads, both local provider routes and destination isolation. A real loopback transport test proves that failing receipt persistence cannot turn a validated upload into an error. These are synthetic source proofs; no installed collector was restarted and no live upload or customer state was modified.

# Codex session-start footprint

New collector `codex_session_start.rs`. It runs inside the existing Claude Code footprint thread right after each footprint cycle (every 6 h; no thread or schedule of its own). It answers what every new Codex session loads before its first request: the AGENTS.md chain and the skills listing. Before this, Codex instruction-file sizes were collected nowhere, and composition dropped the AGENTS.md text entirely (fixed separately in #598).

How it reads: only the prelude of each NEW rollout under every registered Codex root (`snapshot_roots::registered_scan_roots`: `~/.codex` and accepted Ottto slot homes, `sessions` and `archived_sessions`), read against the home that wrote it (its user `AGENTS.md`, skills and `config.toml`) (rows before the first `token_usage_record` / `token_count`, plus up to 8 rows after it when the context window is still unknown; capped at 200 lines and 2 MiB; locally p50 15 lines / 164 KB, p99 334 KB). A local index (`<support>/codex_session_start/index.json`) remembers each final prelude, so a rollout is read once; up to 400 new preludes per cycle. Forks and copied parents (`forked_from_id`, `history_base`, `subagent_history_start_ordinal`, `agent_created_thread`, a second `session_meta`) are not owned fresh starts and are skipped, the same rule as the session sink. Per repository scope the newest owned fresh start (by `session_meta.timestamp`, not file mtime, so a resumed old session cannot hide a newer start) is re-read and uploaded through the existing `POST /api/v1/context-footprint/snapshot` with `agent_source = "codex"`, `counter_source = "codex_rollout_prelude_v1"`, only when the payload changed or weekly.

What it sends: `memory_files` items (kind `memory_file`) for the user-level `~/.codex/AGENTS.md` (`source = "User"`) and each project chain file (`source = "Project"`, repo-relative path), with estimated `tokens` (chars/4, loaded slice), `truncated_by_limit`, and disk counts named like the backend's `ContextFootprintFileMetrics` (#600 / backend #11119): `file_bytes` from `stat`; when the loaded slice is the whole file, the shared `context_file_counts::measure_bytes` of those bytes adds `file_lines`, `file_chars` (UTF-16) and the device-salted `content_hash` (same function and recipe as the Claude file counts, #600). A trimmed or cut file sends only `file_bytes`, never a prefix presented as the file. No `loaded_lines` (that is Claude's line limit). The project text is split into files with a metadata-only `stat` of the root-to-cwd chain, mirroring Codex's loader (override name first, files joined by a blank line, total capped at `project_doc_max_bytes`, default 32 KiB, read from the home's top-level `config.toml` via the secure Codex config reader and `toml_edit`). When files changed after the session started, one file is still attributed; several become one `AGENTS.md (chain)` item. Skills: one `skill` item per listing line with its root kind (Project, User, System, Plugin, Other). Categories `System prompt`, `Memory files`, `Skills`, `Hook context` are chars/4 estimates; `used_tokens` is the exact first-request input.

Order: the backend must accept the four new optional item fields before a daemon release ships this (backend `extra="forbid"`). No release is part of this change.

Known gaps (not in this change): tool-schema size (`additional_tools`, e.g. Codex Desktop's `codex_app`) is not split out (decision D7 pending).

Validation: 17 focused unit tests (`cargo test -p ottto-service --lib codex_session_start`) pass locally; a read-only Python replica over the last 14 days of local rollouts found 151 fresh session directories: 71 global-only, 3 exact chain splits, 3 single-file fallbacks after an edit, 74 removed worktrees skipped, none at the 32 KiB limit.
